# OTel collector integration — specification

**Written before any code, and gated on `SAFETY_BOUNDARIES.md`
Amendment 1.** Two deliverables that share one component: live
cardinality (which unblocks cost arithmetic) and generated routing
configuration (which acts on the result).

Ordering claim: **cardinality first.** The cost calculator is arithmetic
once the inputs exist and guesswork before, and the collector is where
the inputs live. Building the calculator first means multiplying a
column count by a price and calling it savings.

---

## 1. The correction that has to be made first

The phrase "**exact** cardinality counts for real financial math" is not
quite true, and the gap will resurface as a wrong invoice estimate if it
is not written down now.

**What the collector can count exactly:** distinct series flowing
through *this collector*, over *this window*, by metric name and by
label combination. That is a real, precise measurement and it is far
better than anything a CSV can give.

**What that is not:** the vendor's bill.

| Collector sees | Bill is driven by |
|---|---|
| series through this pipeline | series across **all** ingestion paths, including agents and integrations that bypass the collector |
| this window | distinct series over the **billing period**, so a series present for one hour may cost the same as one present all month |
| every series | **custom** metrics only, under a vendor-specific definition of "custom" |
| raw counts | counts after the vendor's own rollups, and after any commitment tier or overage band |

So a collector deployment reports **the cardinality it can see**, and the
saving figure is computed against that with the scope stated in the
output. `estimated_monthly_saving` stays `null` unless the operator
supplies the unit price, exactly as `API_CONTRACT.md` already requires.

**The honest sentence** is *"these series account for N of the M your
collector sees; at the £X per series you told us, that is £Y"* — with
every term traceable. Not *"you will save £Y"*.

## 2. Component A — the cardinality reader

### What it is

A read-only OTel Collector **processor** that observes metrics passing
through and maintains counts. It changes nothing about the pipeline and
emits no telemetry of its own.

### What it produces

```json
{
  "window": {"from": "...", "to": "...", "collector": "gateway-eu-1"},
  "scope": "this collector only; other ingestion paths not visible",
  "metrics": [
    {"name": "http_requests_total",
     "series": 48213,
     "labels": {"instance": 1204, "path": 812, "code": 7},
     "datapoints": 173000000}
  ]
}
```

`series` is the number that matters — the distinct label combinations,
which is what a vendor bills. `labels` gives the per-key spread, because
that is what tells an operator **which label is the problem**. A metric
at 48,000 series with `path` at 812 distinct values has one cause, and
it is usually an unbounded label rather than a redundant metric.

That distinction is worth stating loudly, because **it is not what this
tool was built to find.** Redd Munro finds redundancy *between* metrics.
High cardinality *within* one metric is a different problem with a
different fix (drop a label, do not drop the metric), and the cardinality
reader will surface it constantly. The report must name which it is
seeing, or operators will apply the wrong remedy to the bigger number.

### Constraints, from Amendment 1

- **No network egress of its own.** Writes to the operator's configured
  exporters or to a local file, opens nothing else. No licence check, no
  usage ping, no crash reporting.
- **A test asserts that**, in the same way tests already forbid the
  exported summary from saying "safe to archive".
- **Bounded memory.** A cardinality counter on an unbounded label set is
  itself a cardinality bomb. Counts are held in a bounded sketch with a
  stated error, and the report says which counts are exact and which are
  estimated. An OOM in a customer's gateway caused by the tool that was
  supposed to reduce their costs is the worst available outcome.

### Open question — sampling

Exact distinct counts over a long window need either full retention of
seen-label-sets or a probabilistic structure. HyperLogLog gives ~2%
error at trivial memory. **2% error on a cost estimate is fine; 2% error
on "is this series present at all" is not**, because that decides
whether a metric appears in the audit at all. Proposal: exact for
presence, sketched for magnitude, and the report distinguishes them.

## 3. Component B — the routing generator

### Input

A **completed, attested** worksheet — the same `428` gate as every other
executable export. No attestation, no config.

### Output — routing, per Amendment 1

```yaml
# Generated by Redd Munro from ws.csv
#   audit:     prometheus_infra.csv, basis=differenced, grade A
#   attested:  s.cooper, 11/08/2026
#   effect:    4 series diverted to cold storage. NOTHING IS DELETED.
#   undo:      remove this processor; series resume to the primary
#              exporter. History remains readable in cold storage.
processors:
  routing/redd_munro:
    from_attribute: __name__
    table:
      - value: request_rate_total     # r=0.99987 with methodGET_status200
        exporters: [awss3/cold]
      - value: methodGET_status404
        exporters: [awss3/cold]
```

Every diverted series carries the evidence that justified it as a
comment — unique variance, its identity partner, the attesting reviewer.
A change reviewer should not have to open the tool to approve the diff.

### The hard-drop variant

`filter/redd_munro` with OTTL conditions, generated **only** under
`--allow-drop`, with a header naming exactly which series stop existing
and from when, and the attesting reviewer recorded against the drop
specifically. Never the default, never inferred.

### What is refused, unchanged

Applying the config. The generator writes a file; a human merges it.

## 4. Where this collides with the rest of the product

**Two things now measure "redundancy" and they do not mean the same
thing.** The engine measures shared variance between columns of values.
The cardinality reader measures distinct label combinations. A metric
can be statistically redundant and cheap, or unique and ruinously
expensive. The report must present them as two axes, because the
interesting quadrant — **redundant AND expensive** — is the only one
where the recommendation is obvious, and it is not the largest quadrant.

**The reference graph becomes more valuable and more dangerous.**
Running in the pipeline means the reference graph could be built from
live queries rather than files in git — which is better coverage, and
also the point at which "the graph says nothing uses it" starts feeling
authoritative enough to skip the human. Condition 3 does not move.

**Grade gating still applies.** A collector window of two hours is thin
evidence about a dashboard's structure, whatever its cardinality
precision.

## 5. Build order

| | Deliverable | Depends on | Unblocks |
|---|---|---|---|
| 1 | Cardinality reader, file output | Amendment 1 scope conditions + egress test | everything |
| 2 | Cardinality → audit input | 1 | cost arithmetic, per-label diagnosis |
| 3 | Cost calculator with stated scope | 2 + operator-supplied unit price | the business case |
| 4 | Routing generator | 3 + attested worksheet | the action |
| 5 | Hard-drop variant behind `--allow-drop` | 4 | the minority case |

**Steps 1 and 2 are worth building even if 3, 4 and 5 never happen** —
per-label cardinality diagnosis is independently useful and is a thing
SREs actively want.

## 6. What must be registered before code

Consistent with every other detector here. **These are not written yet.**

- **Cardinality accuracy.** Predictions about sketch error against exact
  counts on a known label distribution, including the pathological cases
  — one unbounded label, and a metric whose series count changes during
  the window.
- **The cost model.** A prediction, made in advance, of how far the
  collector-visible saving lands from an actual invoice change on a real
  deployment. **If nobody will let us check that against a real bill,
  the calculator ships showing its working and never a headline figure.**
- **The two-axes presentation.** That operators shown redundancy and
  cardinality together do not conflate them. Testable with five SREs and
  a mock report, and worth more than any of the code above.
